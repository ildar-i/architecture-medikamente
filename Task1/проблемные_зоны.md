# Анализ проблемных зон безопасности данных компании "Медикаменте"

## 1. Выявленные конфиденциальные данные

### 1.1 Персональные данные (PII)
- ФИО пациентов
- Дата рождения
- Телефон
- Электронная почта
- Адрес прописки
- Место работы/учёбы
- Хронические заболевания
- Медицинские карты
- Результаты анализов
- Заключения врачей

### 1.2 Финансовые данные
- Платежи пациентов
- Финансовые операции
- Данные ККМ
- Бухгалтерские записи

### 1.3 Данные, не учтённые во внутренних системах
- Логи доступа к файлам
- История изменений документов
- Копии данных на локальных компьютерах сотрудников
- Резервные копии без шифрования
- Данные в почтовых ящиках (Exchange)
- Временные файлы на рабочих станциях

## 2. Проблемные зоны безопасности

### 2.1 Хранение данных
**Проблема**: Данные хранятся в неструктурированном виде (Excel, JPG, PDF) на общем диске без шифрования.

**Риски**:
- Отсутствие контроля доступа на уровне файлов
- Невозможность отследить, кто и когда обращался к данным
- Риск утечки при компрометации одного аккаунта
- Отсутствие шифрования данных на диске
- Нет разграничения доступа по ролям

**Соответствие требованиям**: Не соответствует требованиям 152-ФЗ о защите персональных данных.

### 2.2 Обработка данных
**Проблема**: Вся обработка данных производится вручную без аудита действий.

**Риски**:
- Нет журналирования операций с данными
- Невозможность отследить несанкционированный доступ
- Отсутствие контроля целостности данных
- Нет механизмов предотвращения утечек

**Соответствие требованиям**: Не соответствует требованиям по аудиту доступа к персональным данным.

### 2.3 Передача данных
**Проблема**: Внутренние потоки данных между IT-продуктами не контролируются.

**Риски**:
- Отсутствие шифрования при передаче данных
- Нет контроля передаваемых данных
- Возможность перехвата данных в сети
- Отсутствие валидации данных при передаче

**Соответствие требованиям**: Не соответствует требованиям по защите данных при передаче.

### 2.4 Аутентификация и авторизация
**Проблема**: Только доменная аутентификация, нет ограничений на доступ к данным со стороны систем обработки.

**Риски**:
- Отсутствие принципа минимальных привилегий
- Нет разграничения доступа по ролям (RBAC/ABAC)
- Отсутствие многофакторной аутентификации
- Нет контроля сессий пользователей

**Соответствие требованиям**: Не соответствует требованиям по управлению доступом.

### 2.5 Интеграции
**Проблема**: Интеграция с лабораторией отсутствует, данные передаются вручную.

**Риски**:
- Риск утечки данных при ручной передаче
- Отсутствие контроля целостности данных
- Нет механизмов защиты API (если будет реализован)

**Соответствие требованиям**: Не соответствует требованиям по защите данных при интеграциях.

### 2.6 Резервное копирование
**Проблема**: Нет информации о резервном копировании, но если оно есть, вероятно без шифрования.

**Риски**:
- Риск утечки данных из резервных копий
- Отсутствие контроля доступа к резервным копиям

**Соответствие требованиям**: Не соответствует требованиям по защите резервных копий.

### 2.7 Удаление данных
**Проблема**: Отсутствуют механизмы безопасного удаления данных по запросу клиента.

**Риски**:
- Невозможность выполнить требование "права на забвение"
- Данные могут оставаться в резервных копиях и логах

**Соответствие требованиям**: Не соответствует требованиям GDPR и 152-ФЗ.

## 3. Соответствие требованиям законодательства РФ

### 3.1 152-ФЗ "О персональных данных"
**Требования**:
- Определение категорий персональных данных
- Применение правовых, организационных и технических мер защиты
- Контроль за принимаемыми мерами
- Оценка вреда субъектам персональных данных

**Текущее состояние**: Не соответствует большинству требований.

### 3.2 Требования к медицинским данным
**Требования**:
- Особый режим защиты медицинской тайны
- Ограничение доступа к медицинским данным
- Аудит доступа к медицинским данным

**Текущее состояние**: Не соответствует требованиям.

## 4. Рекомендации по улучшению

### 4.1 Немедленные меры (критично)
1. Внедрить шифрование данных на диске (encryption at rest)
2. Внедрить шифрование данных при передаче (encryption in transit)
3. Внедрить систему разграничения доступа (RBAC/ABAC)
4. Внедрить систему аудита доступа к данным
5. Внедрить механизм тегирования конфиденциальных данных

### 4.2 Краткосрочные меры (1-3 месяца)
1. Миграция данных в структурированное хранилище с контролем доступа
2. Внедрение системы управления ключами шифрования
3. Внедрение системы мониторинга и алертинга
4. Разработка политик безопасности данных
5. Обучение персонала работе с конфиденциальными данными

### 4.3 Долгосрочные меры (3-12 месяцев)
1. Внедрение Data Loss Prevention (DLP) системы
2. Внедрение системы Data Lineage
3. Внедрение автоматизированного контроля доступа
4. Внедрение механизмов обезличивания данных для аналитики
5. Внедрение системы управления жизненным циклом данных

## 5. Классификация данных для защиты

### 5.1 Категории данных по уровню конфиденциальности

| Категория | Уровень | Данные | Способы защиты |
|-----------|---------|--------|----------------|
| Медицинские данные | Критический | Медицинские карты, результаты анализов, диагнозы | Шифрование, обфускация, строгий контроль доступа |
| Персональные данные | Высокий | ФИО, дата рождения, адрес, телефон, email | Шифрование, обезличивание, контроль доступа |
| Финансовые данные | Высокий | Платежи, финансовые операции | Шифрование, контроль доступа, аудит |
| Аналитические данные | Средний | Агрегированные данные для BI | Обезличивание, анонимизация |
| Служебные данные | Низкий | Логи, метаданные | Контроль доступа |

### 5.2 Механизм тегирования данных

**Теги конфиденциальности**:
- `CONFIDENTIAL:MEDICAL` - медицинские данные
- `CONFIDENTIAL:PII` - персональные данные
- `CONFIDENTIAL:FINANCIAL` - финансовые данные
- `CONFIDENTIAL:ANALYTICS` - аналитические данные
- `PUBLIC` - публичные данные

**Атрибуты данных**:
- `RETENTION_PERIOD` - срок хранения
- `ENCRYPTION_REQUIRED` - требуется шифрование
- `ACCESS_CONTROL` - уровень контроля доступа
- `AUDIT_REQUIRED` - требуется аудит
- `DELETION_POLICY` - политика удаления

## 6. Инструменты и меры защиты

### 6.1 Шифрование
- **At Rest**: AES-256, TDE (Transparent Data Encryption) для БД
- **In Transit**: TLS 1.3, VPN для внутренних соединений
- **Key Management**: HashiCorp Vault, AWS KMS, или аналоги

### 6.2 Контроль доступа
- **RBAC**: Роли на основе должностей (врач, администратор, бухгалтер)
- **ABAC**: Атрибуты на основе контекста (время, место, устройство)
- **Zero Trust**: Проверка каждого запроса

### 6.3 Аудит и мониторинг
- **Audit Logging**: Логирование всех операций с данными
- **SIEM**: Система для анализа логов и выявления аномалий
- **DLP**: Предотвращение утечек данных

### 6.4 Обфускация и обезличивание
- **Tokenization**: Замена чувствительных данных токенами
- **Pseudonymization**: Псевдонимизация для аналитики
- **Data Masking**: Маскирование данных в не-продакшн окружениях

### 6.5 Управление жизненным циклом данных
- **Data Retention**: Автоматическое удаление данных по истечении срока
- **Data Lineage**: Отслеживание происхождения и использования данных
- **Right to be Forgotten**: Механизм удаления данных по запросу
